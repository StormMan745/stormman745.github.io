# Защита PetCare

Проверено и усилено 30 октября 2026 года. Это описание конкретных мер и проверок, а не гарантия отсутствия всех уязвимостей.

## Данные аккаунтов

- `petcare_data` и `pets` защищены RLS: чтение и изменение разрешены только владельцу `auth.uid()`. У `anon` нет прав на эти таблицы.
- Фото и коллажи `petcare-stories` приватны. Путь файла начинается с UUID владельца; правила чтения, загрузки, замены и удаления проверяют этот UUID.
- Неиспользуемый пустой bucket `Photo` переведён в приватный режим. На момент проверки ссылок на него в профилях и карточках питомцев не было.
- JSON профиля должен быть объектом размером до 16 MiB. Проверка выполняется базой, а не только браузером. Самый большой существующий профиль на момент изменения был меньше 90 KiB.
- Служебные функции находятся в `petcare_private`; публичные RPC используют `SECURITY INVOKER`. Привилегированные реализации проверяют аккаунт и имеют пустой `search_path`.
- Новые таблицы и функции в `public` не получают автоматически доступ для `anon` и `authenticated`. Нужны явные GRANT и RLS.

## Ассистент

- Каждый запрос подтверждает пользователя через Auth, читает только его профиль под его JWT и применяет RLS.
- Лимиты общие для всех вкладок и серверных экземпляров: 12 ответов в минуту и 250 в сутки на аккаунт; проверки профиля — 60 в минуту и 3000 в сутки. Суточное окно — UTC. Это ограничения API, не защита от распределённой атаки на инфраструктуру.
- Счётчики атомарны, находятся в закрытой таблице и недоступны для сброса из браузера. При превышении возвращается 429 с `Retry-After`; при недоступности проверки лимита запрос к модели не отправляется.
- Принимается JSON размером до 64 KiB; проверяется Origin, ответы имеют `Cache-Control: no-store` и `nosniff`. Для локального `index.html` разрешён opaque Origin `null`, но JWT и проверка пользователя обязательны.

## Уведомления

- Удаление, обновление и проверка push-подписки ограничены её владельцем. Другая учётная запись не может перезаписать подписку.
- При подключении уведомлений в новом аккаунте браузер заменяет неподходящую подписку новой. При смене аккаунта во время подключения операция останавливается.
- Разрешены HTTPS-адреса браузерных push-служб Google, Mozilla, Apple и Microsoft. Проверка есть и при записи в базу, и непосредственно перед отправкой. URL с чужим доменом, пользовательскими credentials, нестандартным портом и локальные адреса отклоняются. Новые провайдеры нужно добавлять в обе проверки после проверки их официальной документации.
- Проверяются формат ключей, размер подписки и максимум 20 устройств на аккаунт. Регистрация ограничена 30 запросами в минуту и 500 в сутки.
- Диспетчер требует отдельный секрет планировщика. `verify_jwt=false` оставлен намеренно: расписание аутентифицируется этим секретом. Отправка имеет тайм-аут 10 секунд.

## Браузер и публикация

- CSP разрешает локальные скрипты и только точный URL закреплённого Supabase SDK с существующей SRI-проверкой. Произвольные скрипты с CDN, inline-скрипты, обработчики HTML-атрибутов, `eval` и подмена `<base>` не разрешены.
- `frameguard.js` подключается и при локальном открытии. Это дополнительная клиентская мера; HTTP `frame-ancestors`/`X-Frame-Options` этим изменением не добавлялись.
- Карта Яндекса, анимированные модели, правила входа и регистрации сохранены.
- Service Worker хранит оболочку сайта и не кэширует внешние запросы к Supabase. В браузере остаются необходимые для работы сессия и локальная копия данных аккаунта; это не сквозное шифрование.
- Проверка файлов проекта не обнаружила приватных ключей по проверенным шаблонам. `sb_publishable_*` и публичный VAPID-ключ предназначены для клиента; секреты сервера должны оставаться в Supabase Secrets/Vault.

## Проверки

- Транзакционные SQL-проверки: собственное чтение/запись; отказ в чужом чтении/изменении и загрузке файлов; проверка размера данных; квоты; запрет перехвата/удаления чужой подписки; блокировка небезопасных URL. Все тестовые изменения откатывались.
- Тесты Edge Functions: обычный ответ и чтение профиля, авторизация, 429, 413, Origin, выбор питомца, секрет cron и запрещённые адреса. Внешний ИИ и отправка уведомлений в тестах имитировались.
- Проверки браузера при ширине 390 и 1440 px: кнопки входа/регистрации, CSP, экранирование текста в PDF, смена push-подписки и остановка при смене аккаунта. Успешный вход с настоящим паролем пользователя не выполнялся.
- Реальные HTTP-проверки: запрос ассистенту без сессии — 401; push-диспетчер без секрета — 401; анонимное чтение данных запрещено; схемы `net` и `petcare_private` не опубликованы в REST API (406/PGRST106).

Повторить локальные тесты серверных функций: `npm ci --prefix tools`, затем из корня проекта `npm run --prefix tools test:security`.
`tools/security-database-check.sql` выполняется целиком в одной транзакции с ROLLBACK; нужны два существующих профиля и административный SQL-доступ. Не удаляйте BEGIN/ROLLBACK.

## Оставшиеся настройки инфраструктуры

- Проверка утёкших паролей в Supabase пока выключена. Согласно [документации](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection), она требует Pro или выше. Тариф не менялся.
- CAPTCHA и дополнительная MFA не подключались; серверная политика паролей Supabase не менялась. Не добавляйте обязательную CAPTCHA без ключей провайдера и проверки рабочего сценария входа.
- Supabase Advisor продолжает сообщать о `pg_net` в `public`. Расширение не переносится (`extrelocatable=false`), а его функции принадлежат управляемой роли `supabase_admin`. Попытка REVOKE от `postgres` не изменила эти системные права; миграция зафиксирована в истории, но не считается устранением предупреждения. Схема `net` через REST не доступна. Для изменения управляемых прав требуется Supabase. Не удаляйте расширение: оно нужно расписанию уведомлений. [Описание предупреждения](https://supabase.com/docs/guides/database/database-linter?lint=0014_extension_in_public).
- Сообщения Advisor `RLS Enabled No Policy` для служебных таблиц ожидаемы: прямой клиентский доступ к ним запрещён. [Описание проверки](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).
- Защита GitHub/Supabase-аккаунта владельца, восстановление резервных копий и инфраструктурная защита от DDoS требуют отдельных настроек. Владелец должен использовать MFA и хранить коды восстановления отдельно.
